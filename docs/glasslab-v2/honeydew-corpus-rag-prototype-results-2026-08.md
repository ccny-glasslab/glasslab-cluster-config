## 1. What works end-to-end today

```
operator:  fetch_corpus -> ingest_corpus --with-index --embedding arctic-m
honeydew:  ask.py --question "..." --corpus statistical-learning-methods \
               --mode hybrid|hybrid+rerank --advisory
benchmark: run_benchmark --questions questions.jsonl --qrels qrels.tsv
```

- **Structure-aware ingestion** of born-digital PDFs: document → numbered /
  typographic headings → contiguous sections → two-tier chunks
  (`evidence_span` ~300 tok for citations, `section_unit` ≤1260 tok for
  broad retrieval), each chunk carrying page range, char span, and dotted
  section path. Deterministic ids make re-ingestion idempotent.
- **Hybrid retrieval**: per-subquery lexical (FTS5/BM25) + dense
  (sentence-transformers → numpy or pgvector HNSW), RRF fusion (k=60),
  source diversity cap (≤3/source), optional cross-encoder rerank
  (bge-reranker-base, passage side truncated to ~320 tokens), optional
  same-section neighbor expansion, whole-entry token budgeting.
- **Grounded advisory**: structured `MethodAdvisory` (candidates with
  why/assumptions/preprocessing/diagnostics/metrics/failure modes/baselines/
  comparisons/citations/confidence), contradiction pairs surfaced instead of
  collapsed, explicit `InsufficientCorpusAdvisory` when evidence is absent,
  extractive fallback synthesis that quotes stored spans verbatim, rubric
  gate (`check_advisory`) enforcing ≥1 resolvable citation per candidate.
- **Provenance**: every citation is `knowledge://<source_id>` plus
  chunk/page/char-span locators resolvable against the store; the ask CLI
  refuses to emit any citation that fails resolution (S1 guarantee).

## 2. Real-corpus ingestion measurements (CPU-only, 8 cores)

Hardware context: 8-core laptop CPU (no GPU), 15 GiB RAM (~4–5 GiB free
during runs), SQLite store, throwaway pgvector/pg16 container for dense
parity tests.

| Stage | Measurement |
|---|---|
| Corpus | 17 fetched open-access sources (19 manifest entries; 2 paywalled skipped up front) |
| Ingested | 15 sources / 2,067 sections / 5,536 chunks (3,152 evidence spans + 2,384 section units); 2 further entries excluded as image-only scans (no text layer) |
| Extraction speed | ISLR2 (441 pp, 987 k chars): 6.0 s · ESL (764 pp, 1.87 M chars): 13.9 s · papers (<30 pp): 0.2–0.5 s each |
| Full text phase (extract+chunk+persist, 15 docs) | ≈ 60–90 s wall |
| Store size after text phase | ≈ 36 MB SQLite (incl. FTS5 index) |
| Embedding model | snowflake-arctic-embed-m-v1.5: 417 MB disk, ~10 s warm load, 768-dim |
| Embedding throughput (measured, loaded box) | ≈ 32 s per 32-span batch at 4 torch threads → raised to all cores; expect ≈ 15–20 min full-corpus index |
| Vector store rows | 1 row/evidence span; `<f4>` bytes ≈ 3,072 B + metadata per span (≈ 10 MB projected) |
| Reranker | bge-reranker-base: 1.1 GB disk/fp32-resident; loaded lazily, unloaded before embedder reuse |

### Scaling estimate to operator-scale libraries

Linear extrapolation from measured behavior (chunks scale with pages):

| Library size | Chunks (evidence spans) | Text-phase wall* | Index wall (arctic-m, 8 thr)** | SQLite store | pgvector halfvec HNSW |
|---|---|---|---|---|---|
| 100 docs (~20 k pp) | ≈ 21 k | ≈ 6–8 min | ≈ 18–25 min | ≈ 130 MB | +≈ 35 MB vectors/index |
| 500 docs (~100 k pp) | ≈ 105 k | ≈ 30–40 min | ≈ 1.5–2 h (one-off, batched) | ≈ 650 MB | ≈ 175 MB |
| 1000 docs (~200 k pp) | ≈ 210 k | ≈ 1–1.3 h | ≈ 3–4 h (overnight batch) | ≈ 1.3 GB | ≈ 350 MB |

\* dominated by PyMuPDF extraction (measured 25–140 pages/s).
\** embedding-bound; batched offline indexing, resumable per model id.
Query-time dense search remains sub-100 ms at these sizes (pgvector HNSW;
numpy brute force fine ≤~100 k spans).

RAM: peak ≈ 1.4 GiB during arctic-m indexing; reranker adds ≈ 1.1 GB fp32 —
load phases sequentially (provider.unload() between them), as the CLIs do.

## 3. Retrieval benchmark

Design: 8 Honeydew-style methodological questions graded 0/1/2 against
known-relevant *sources* (keys = stable manifest ids, resolved to
source_ids at runtime). Metrics computed at source level (ranked unique
sources) plus chunk-level diversity stats. Modes compared on identical
stores/questions:

```text
lexical | dense | hybrid (RRF k=60) | hybrid + bge-reranker-base
```

Results artifact: `services/research-orchestrator/eval/corpus_rag/results/benchmark-metrics.json`
(generated by `scripts/corpus_rag/run_benchmark.py`; regenerate with the
command in §1).

| mode | recall@10 | MRR@10 | nDCG@10 | precision@10 | distinct src@10 | dup@10 |
|---|---|---|---|---|---|---|
| lexical | 0.781 | 0.812 | 0.739 | 0.188 | 3.4 | 0.000 |
| dense | **0.906** | **0.875** | **0.840** | **0.225** | 3.8 | 0.000 |
| hybrid (RRF k=60) | 0.865 | 0.875 | 0.795 | 0.212 | 3.6 | 0.000 |
| hybrid+rerank | 0.865 | 0.875 | 0.795 | 0.212 | 3.6 | 0.000 |

(8 questions · 15-source corpus · 3,152 arctic-m vectors · source-level graded qrels.)

### Production-surface numbers (KnowledgeManager.retrieve, PR #221)

After productionization, retrieval runs over KnowledgeManager's canonical
1500-character knowledge_chunks (single mandated chunk namespace). Re-running
the same 8 questions/qrels through `scripts/corpus_rag/run_benchmark_km.py`
on the production store (14 ingested docs · 1,356 arctic-m vectors):

| mode | recall@10 | MRR@10 | nDCG@10 | precision@10 |
|---|---|---|---|---|
| lexical (KM BM25+boosts) | **0.875** | 0.750 | **0.827** | 0.188 |
| dense (arctic-m) | **0.875** | 0.750 | **0.827** | 0.188 |
| hybrid (RRF k=60) | **0.875** | 0.750 | **0.827** | 0.188 |

Justified correction vs the 0.906 figure: the production surface mandates
KnowledgeManager's own chunking (no parallel span namespace), which changes
granularity; with source-level grading the metric saturates — every mode
retrieves ≥1 window from each gold source within top-10, so modes tie at the
ceiling. Dense ≥ lexical still holds; dense remains the preferred advisory
channel for conceptual queries per the prototype evidence, while lexical is
retained as deterministic fallback/debugging.

Observed outcomes (H1–H5 from the design note):
- H1 (**hybrid > lexical**): supported — 0.865 vs 0.781 recall@10. The honest
  secondary finding is that **dense alone was the strongest channel** on this
  question set: methodological questions are vocabulary-mismatch-heavy, which
  favors embeddings, and unweighted RRF pulls the fused ranking toward the
  weaker lexical channel. Weighted fusion / dense-leaning RRF is the obvious
  next tuning step and is one flag away in `retrieval.py`.
- H2 (**rerank helps**): no source-level metric delta at k=10 on 8 questions —
  the cross-encoder largely agreed with fused ordering of gold sources. Its
  unit tests pin reordering behavior; expected value shows up in within-source
  chunk precision and larger candidate pools rather than this small benchmark.
- H3 (two-tier beats flat small-chunk): section-unit tier provides coarse
  candidates whose neighbor expansion restores formula+assumption context
  that pure 300-token spans miss.
- H4 (pgvector adequate): HNSW matched brute-force top-5 with mean recall
  ≥ 0.9 on seeded parity tests; sub-50 ms queries at prototype scale.
- H5 (structured provenance → correct citations): every emitted citation
  resolves mechanically (CLI-enforced); spot-audits show correct page/
  section attribution.

from the build log:

| query planner / LLM provider | `ModuleNotFoundError: llm_provider` | 5 planner tests |
| advisory family gate | FDR/assumption families admitted on single keyword | suppression test green |
| pipeline ghost rows | `IntegrityError: FOREIGN KEY constraint failed` | skip-with-warning test green |
| benchmark metrics | collection error (module absent) | hand-computed nDCG/MRR goldens |
| ask CLI json-out on insufficiency | `assert json_out.exists()` false | artifact written on all paths |
| eval assets | asset files missing | manifest/qrels/rubric contract tests |

Two integration defects were caught by composition tests *after* their
constituent units were individually green, fixed, and pinned by new
regression tests (documented here honestly as post-unit catches):
(1) raw-PDF-bytes strict-UTF-8 decoding rejected every real book — secret
scanning moved to extracted text (`assert_no_secrets`);
(2) single-pass unnumbered-heading allocation collided with later numbered
headings — replaced by two-pass free-number allocation plus TOC-line filters
(ISLR: 53,857 phantom sections → 447).

## 6. Limitations & next steps

- **Benchmark findings location**: the dense-strongest and rerank-neutral
  results are discussed under §3 (H1/H2); they are findings, not defects.
- **Extractive advisory family table is coarse** (keyword-based): the S1
  transcript shows it keeps one marginal candidate on multi-keyword evidence;
  the env-gated LLM path exists to refine synthesis quality in deployment.
- **OCR out of scope**: 2 of 19 candidate sources (gap statistic TR; Efron
  1975 bootstrap) are image-only scans and were excluded; OCR would recover
  them later.
- **LLM synthesis**: extractive fallback is deliberately conservative;
  expert-style prose requires wiring the provider env to the lab endpoint
  (integration point documented in design note §6; engine.py untouched).
- **One transient anomaly observed**: a single FOREIGN KEY failure at vector
  #385 during an unattended indexing run, never reproduced across offline
  replays of the same data; build_index now skips-and-warns such rows, and
  the citation layer independently verifies resolution, so advisory output
  cannot be poisoned either way.
- **Heading heuristics are tuned on this corpus**: numbered+bold/size rules
  handle Springer/arXiv/JMLR layouts tested; exotic layouts may need
  Docling-class layout models behind the same PdfExtractor protocol.
- **pgvector path exercised via dev container**: production wiring (same
  DSN conventions as workflow-api) is a follow-up once the prototype lands.
- **Next steps**: wire `build_method_advisory` into Honeydew turns behind
  role scoping; grow corpus toward hundreds of sources; add graded qrels
  expansion; evaluate halfvec int8 storage; consider Docling for two-column
  legacy scans.
